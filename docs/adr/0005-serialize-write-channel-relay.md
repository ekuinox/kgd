# 0005: 書き込みチャンネルの転記は単一ワーカーで直列化する

## ステータス

受理 (2026-06-12, #71 / #77 の転記機能に対する修正)

## 文脈

serenity は Discord のイベントをイベントごとに独立した tokio タスクで並行実行する。
書き込み用チャンネルの転記 (#77) は「Notion 同期 → スレッドへ転記」の順で処理するため、
画像のように同期へ時間のかかるメッセージが、後続のテキストメッセージに追い越され、
スレッドへの転記順が投稿順と一致しないことがあった。Notion のブロック順にも同じ競合がある。

検討した選択肢:

1. 転記処理全体を Mutex で直列化する (シンプルだがタスク実行開始順への依存が残る)
2. mpsc キュー + 単一ワーカーで直列化する
3. 転記を先・Notion 同期を後に入れ替える (順序の完全保証にならず、ロールバック設計の反転も必要)

## 決定

案 2 を採用する。イベントハンドラは WriteChannelEvent (Posted / Updated / Deleted) を
bounded な mpsc キュー (容量 64) へ送るだけで即座に返り、単一ワーカー (run_relay_worker) が
到着順に 1 件ずつ転記処理を行う。

順序保証の根拠: Discord gateway は同一シャード内のイベント順序を保証し、ハンドラは受信後
即座に enqueue し、mpsc は FIFO で、ワーカーは 1 件完了するまで次を取り出さない。

## 結果

- スレッドへの転記順と Notion のブロック順が投稿順に揃う
- 同期に時間のかかるメッセージの処理中は後続の転記も待つ (日記用途では許容)
- キューが満杯の場合は send が待つことで自然なバックプレッシャーになる
- 通常の日報スレッドへの直接投稿の Notion 同期には同じ競合が残っている。
  問題になる場合は同様の直列化を検討する
