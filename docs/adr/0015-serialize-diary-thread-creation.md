# 0015: 日報スレッドの作成はロックで直列化し、作成直前に再確認する

## ステータス

受理 (2026-10-14, 同じ日報日のスレッドが二つ作られた不具合に対する修正)

## 文脈

2026-10-14 の本番で、同じ日報日 (2026-10-14) のスレッドが 1.3 秒差で二つ作られた。
クローズ & 新規作成ボタンを短い間隔で二度押したことが発端で、ログの並びは次のとおり。

```
02:08:40.74 1 件目: Notion ページを新規作成
02:08:41.99 1 件目: スレッド 1559749758485004299 を作成
02:08:42.49 2 件目: 同じ Notion ページを検索で発見
02:08:43.33 2 件目: スレッド 1559749764722204732 を作成
```

serenity はイベントごとに独立した tokio タスクで処理するため、二度の押下は並行に走る。
処理は `close_and_new_precheck`（存在確認）と `close_and_create_new`（作成）に分かれており、
1 件目が `repo.insert` するより前に 2 件目の存在確認が走ると、どちらも `ReadyToCreate` と判定して
二つ作ってしまう。典型的な check-then-act の競合で、`/diary new` とボタンの同時実行にも同じ競合がある。

検討した選択肢:

1. `diary_entries(date)` に UNIQUE 制約を足す
2. 作成処理を `tokio::sync::Mutex` で直列化し、ロックの中で存在確認をやり直す
3. mpsc キュー + 単一ワーカー (ADR-0005 と同じ形)

案 1 は、スレッド作成 (Discord) とページ作成 (Notion) が insert より前に起きるため、
重複した副作用そのものは防げない。既存データに重複があると起動時マイグレーションが落ちる弱さもある。
案 3 は、ボタンの応答を 3 秒以内に返すために「確認は即時・作成は後」という今の形と噛み合わず、
キューイングの割に得られるものが少ない。

## 決定

案 2 を採用する。`ManageDiaryLifecycleUseCase` に `creation_lock: Mutex<()>` を持たせ、
`close_and_create_new` と `create_or_reopen` の全体をこのロックの中で実行する。
ロックを取った直後に `get_by_date` で対象の日報日を再確認し、既にあれば作成へ進まず
`CloseAndNewOutcome::AlreadyExists` を返す。

応答を 3 秒以内に返すための `close_and_new_precheck` はロックを取らないままにする。
これはあくまで早期の案内用で、作成の可否はロックの中の再確認が決める。

## 結果

- ボタンを二度押しても、作られるスレッドと日報エントリは一つだけになる
- 二度目の押下には「今日の最新の日報はこちらです: <#...>」を返し、
  「作成しています...」の表示のまま残らない
- 作成中は後続の押下やコマンドが待つ (日報用途では許容)
- 直列化はプロセス内に閉じている。bot を多重起動した場合は防げないが、
  運用は単一コンテナなので対象外とする
- `diary_entries(date)` の UNIQUE 制約は、既存の重複を片付けた後なら
  多重防御として足せる (2026-10-14 時点で 2026-02-01 の重複が残っている)
