# 0007: 日報の一日は day_start_hour から始まる

## ステータス

受理 (2026-08-10, 0 時を過ぎた投稿が転記されなかった障害への対応)

結果のうち「深夜にボタンを押しても新規作成されない」は
[ADR-0008](0008-start-next-diary-day-before-day-start-hour.md) で改めた。
日付境界の定義そのものは有効である。

## 文脈

2026-08-08 のデプロイ ([ADR-0006](0006-retry-notion-requests-and-surface-failures.md)) で、
書き込みチャンネルの転記を「今日の日報が無ければ転記しない」に変更した。
それ以前は最新の日報へフォールバックしており、その日の投稿が前日の日報へ
まとめて同期される問題があったためである。

この変更により、0 時を過ぎてから翌朝に日報を作るまでの投稿がすべて転記されなくなった。
2026-08-09 の 00:02 から 04:34 にかけて 9 件、2026-08-10 の 00:12 に 1 件が
`No diary entry for today to relay write channel message` として捨てられている。
転記されなかった投稿を後から取り込む仕組みは無いため、これらは失われた。

原因は「日報の一日」を暦日、すなわち 0 時境界で定義していたことである。
運用上は深夜の投稿もその日の日報の続きとして扱いたいのに、
0 時を過ぎた瞬間に日報日が変わり、まだ存在しない日報を探しにいっていた。

一方で自動クローズ通知の時刻 (`auto_close_hour`, 既定 8) は、すでに
「ここで一日を区切って次の日報へ移る」という意味を持っていた。
区切りの概念が日付境界と通知時刻の 2 つに分かれていたことが、ずれの温床だった。

## 決定

**日報の一日の始まりを `day_start_hour` で定義し、日付境界と自動クローズ通知の
両方に使う。** `auto_close_hour` は廃止するが、設定ファイルの書き換えを不要にするため
serde の `alias` で旧名も受け付ける。既定値は `auto_close_hour` の 8 を引き継ぐ。
`auto_close_enabled` は通知を出すかどうかの制御として残す。

**区切りの知識はドメイン層の `DiaryCalendar` に集約する。** タイムゾーンと
`day_start_hour` を持つ値オブジェクトとし、`today` / `local_date` / `format` を提供する。
`today` の戻り値は日報日の暦日 0 時をタイムゾーン基準で表した UTC 時刻とし、
`day_start_hour` を変えてもこの表現は変わらない。永続化済みの `diary_entries.date` と
互換なので、データ移行は不要である。

**`should_attempt_auto_close` から時刻の比較を除く。** 日報日の切り替わり時刻は
`DiaryCalendar` が持つため、判定は「機能が有効か」と「同じ日報日に通知済みか」だけになる。
日報日より前の再起動で誤通知が出ないことは、最新エントリが同じ日報日なら
何もしないという後段のガードが担保する。

**`day_start_hour` は 0-23 を設定読み込み時に検証する。** 範囲外の値を許すと
すべての時刻が前日扱いになり、日報日が進まなくなる。

## 結果

0 時から `day_start_hour` までの投稿は、暦日で前日にあたる日報スレッドと
Notion ページに転記される。ADR-0006 が避けたかった「過去の日報への紛れ込み」は
起きない。紛れ込みではなく、同じ日報日の続きだからである。

深夜に「クローズ & 新規作成」を押しても新しい日報は作られず、既存の日報が再開される。
新しい日報が始まるのは `day_start_hour` 以降になる。

設定ファイルを書き換えなくても動く。`auto_close_hour = 7` は `day_start_hour = 7` として
読まれ、日付境界と通知時刻の両方が 7 時になる。

障害で転記されなかった 10 件は、この変更では復旧しない。
書き込みチャンネルに残っている元メッセージを投稿し直す必要がある。
